## Part 1: storing passwords

### The problem

The SMW `users` table stores `admin` / `admin` in plain text. If anyone ever gets a copy of the database (a stolen backup, an SQL injection, a curious co-worker), they get every password. Because people reuse passwords, that often unlocks their email and bank too.

So the database must store something that lets us **check** a password **without being able to recover it**.

### Hashing, not encryption

| | Encryption | Hashing |
| --- | --- | --- |
| Reversible? | Yes, with the key | **No**, one-way |
| Used for | Data you need back (messages, files) | Passwords |
| If the database leaks | The key often leaks with it, so everything is readable | Attackers must guess each password one by one |

A **hash function** turns any input into a fixed-length fingerprint. The same input always gives the same fingerprint, but you cannot run it backwards. To check a login you hash what the user typed and compare fingerprints.

<Mochi>
Hashing is like a smoothie. From the same fruit you always get the same smoothie, so you can check "was this made from strawberries and banana?" by making another one and comparing. But nobody can turn a smoothie back into fruit.
</Mochi>

### Salt and slowness

Plain hashes like MD5 or SHA-1 are not enough:

- **Same password, same hash.** Attackers precompute huge tables of hashes for common passwords ("rainbow tables") and look them up instantly. The fix is a **salt**: random extra data mixed into every password before hashing, stored next to the hash. Two users with the password `secret123` now get completely different hashes.
- **Fast hashes are fast to guess.** A graphics card can try billions of MD5 hashes per second. Password hashes must be **deliberately slow** (bcrypt, Argon2), so each guess costs real time.

### The PHP way: two functions

PHP does all of this correctly for you:

```php
$hash = password_hash($password, PASSWORD_DEFAULT);   // when registering
// $2y$10$Q4c7Vh1Fz3Lr8q2....kJ7a   (60 characters, salt included)

if (password_verify($typed, $hash)) { /* correct */ }  // when logging in
```

```text
$2y$ 10 $ Q4c7Vh1Fz3Lr8q2xT9sKue  Jm0b4cP8T0rXx2hQyN3nZ5Yw1mM9kJ7a
 │    │     └── 22-char salt ──┘   └────────── the actual hash ──────────┘
 │    └── cost: 2^10 rounds (slowness)
 └── algorithm: bcrypt
```

- `PASSWORD_DEFAULT` uses bcrypt today and may switch to a stronger algorithm in future PHP versions. That is why the column is `VARCHAR(255)`: room to grow.
- The salt is generated automatically and stored **inside** the hash string, so `password_verify` can read it back.
- Never compare hashes yourself with `==`, and never hash the password and search for it with `WHERE password_hash = ?`. Each call to `password_hash` produces a different string because of the salt. Fetch the row by email, then `password_verify`.

The fitness site's registration and login:

```php
// register.php
$pdo->prepare('INSERT INTO users (email,password_hash,role) VALUES (?,?,?)')
    ->execute([$email, password_hash($pass, PASSWORD_DEFAULT), $role]);

// login.php
$s = $pdo->prepare('SELECT id,email,role,password_hash FROM users WHERE email=?');
$s->execute([trim($_POST['email'] ?? '')]);
$u = $s->fetch();
if ($u && password_verify($_POST['password'] ?? '', $u['password_hash'])) { ... }
```

<Tip>
Show the same message for "no such email" and "wrong password" ("Wrong email or password."). Different messages tell an attacker which emails have accounts.
</Tip>

## Part 2: two-factor authentication

### Why one factor is not enough

Passwords get phished, reused and guessed. **Two-factor authentication** requires two different kinds of proof:

| Factor | Example |
| --- | --- |
| Something you **know** | password |
| Something you **have** | your phone with the authenticator app |
| Something you **are** | fingerprint, face |

A stolen password alone is now useless; the attacker would also need your phone.

### The idea behind authenticator codes

Google Authenticator does **not** talk to the server. It does not need internet. So how can the server know the code on your phone?

1. **Once, at setup**, the server creates a random **secret** and shows it to you as a QR code. Your phone stores it. Now both sides know the same secret, and nobody else does.
2. **Every 30 seconds**, both sides independently compute a code from *the secret* and *the current time*.
3. When you type the code, the server does the same calculation and compares. Same secret + same time = same code.

This is **TOTP**, *Time-based One-Time Password* (standard RFC 6238). Here is a live one, computed in your browser with the same algorithm:

<Mochi>
It is like two people who own identical magic dice that roll the same number every 30 seconds. They never call each other, but if you tell one of them the number, they can check it against their own die.
</Mochi>

### Step by step

```text
secret (random 20 bytes)       time now: 1795462800 seconds since 1970
        │                                      │
        │                        counter = floor(time / 30) = 59848760
        ▼                                      ▼
     HMAC-SHA1( key = secret , message = counter as 8 bytes )
        │
        ▼  20-byte result, e.g.  1f 86 98 69 0e 02 ca 16 61 85 50 ef 7f 19 da 8e 94 5b 55 5a
        │
        ▼  dynamic truncation: take the last 4 bits (here 0xa = 10) as an offset,
        │  read 4 bytes starting at position 10 → 0x50ef7f19, drop the top bit
        ▼
     1357872921  →  % 1 000 000  →  872921   ← the 6-digit code
```

- **HMAC** is a hash that mixes in a key. Without the secret, the output looks completely random, so seeing old codes does not help predict new ones.
- The **counter** changes every 30 seconds, so the code does too.
- **Truncation** turns 20 bytes into a 6-digit number humans can type.

### Base32 and the QR code

The secret is random bytes, which you cannot type. It is encoded in **Base32**: only the letters A–Z and digits 2–7 (no 0/O or 1/I confusion), for example `JBSWY3DPEHPK3PXP`.

The QR code contains a **provisioning URI**, a standard address the authenticator apps understand:

```text
otpauth://totp/Kraftwerk%20Fitness:ishika%40example.de?secret=JBSWY3DPEHPK3PXP&issuer=Kraftwerk%20Fitness&algorithm=SHA1&digits=6&period=30
```

The app reads the account name, the issuer (shown as the title in the app), the secret and the settings.

`random_bytes` is a **cryptographically secure** random generator. Never use `rand()` or `mt_rand()` for secrets: they are predictable.

Computing one code (HOTP is the counter-based version; TOTP just feeds it the time):

<Source file="Learning/Week3_Login/GoogleAuth/totp.php" from={41} to={56} />

- `pack('N*', 0) . pack('N*', $counter)` turns the counter into 8 bytes (big-endian), as the standard requires.
- `hash_hmac('sha1', …, true)` returns the raw 20-byte HMAC.
- `ord(substr($hash, -1)) & 0x0F` reads the last 4 bits as the offset.
- The four `<< 24 | << 16 | << 8 |` lines glue four bytes into one 31-bit number (`& 0x7f` drops the sign bit).
- `% 1000000` keeps the last six digits.

Verifying with a little tolerance for clock differences:

<Source file="Learning/Week3_Login/GoogleAuth/totp.php" from={58} to={66} />

`$window = 1` accepts the previous, current and next 30-second code. Phones and servers are rarely perfectly in sync, and typing takes time. `sprintf('%06d', …)` pads codes like `42891` to `042891`.

Why confirm a code before enabling? If the user closed the page before scanning, or scanned it wrongly, enabling 2FA would lock them out forever. Requiring one correct code proves the phone really has the secret.

### One function checks every code

<Source file="Project/fitness_center/config.php" from={95} to={107} />

`code_ok` is used by setup, verify **and** logout. It also feeds the **lockout**: five wrong attempts in a row (passwords or codes) lock the account for 15 minutes. Without this, a 6-digit code (one million possibilities, three valid at a time) could be brute-forced by a script in a few hours.

## Database tables for 2FA

```sql
CREATE TABLE user_2fa (
  user_id INT PRIMARY KEY,                         -- one secret per user
  secret_base32 VARCHAR(64) NOT NULL,
  enabled TINYINT(1) NOT NULL DEFAULT 0,           -- 0 until the first code was confirmed
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);
```

The professor's version also has a `user_2fa_backup_codes` table: one-time codes the user can print and use if they lose their phone. They are stored **hashed**, like passwords. The fitness site skipped them to stay small; an admin can reset a user by deleting their `user_2fa` row.

<Note title="Known limits of this implementation">
A code stays valid for its whole window, so someone who sees it over your shoulder could reuse it within about a minute; storing the last used counter would prevent that. The secret is stored unencrypted in the database. Both are acceptable for a course project and are listed in [Web security essentials](/wiki/web-security).
</Note>

Write `hash_test.php` that hashes the password `kraftwerk2026` twice and prints both hashes, then verifies the password against both, and verifies `kraftwerk2025` against the first. Explain why the two hashes differ but both verify.

<Solution>
```php:hash_test.php
<?php
$h1 = password_hash('kraftwerk2026', PASSWORD_DEFAULT);
$h2 = password_hash('kraftwerk2026', PASSWORD_DEFAULT);
echo "$h1<br>$h2<br>";
var_dump(password_verify('kraftwerk2026', $h1));   // true
var_dump(password_verify('kraftwerk2026', $h2));   // true
var_dump(password_verify('kraftwerk2025', $h1));   // false
```
Each hash contains its own random **salt** (the 22 characters after `$2y$10$`). `password_verify` reads the salt from the stored hash, hashes the typed password with that same salt, and compares. So identical passwords never produce identical database entries, yet both still verify.
</Solution>
